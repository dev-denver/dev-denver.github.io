# 캡처 프롬프트 (외부 레포용)

다른 프로젝트(백엔드·프론트엔드·사이드 프로젝트 등)에서 공부하거나 문제를 해결한 뒤,
그 내용을 블로그 글의 **재료**로 뽑아낼 때 쓰는 프롬프트다.

## 쓰는 법

1. 아래 `--- 복사 시작 ---` ~ `--- 복사 끝 ---` 사이를 통째로 복사한다.
2. 그 레포의 AI 세션에 붙여넣고, 마지막 줄에 무엇을 정리할지 한 줄 덧붙인다.
   (예: "방금 작업한 JWT 리프레시 토큰 재발급 이슈를 정리해줘")
3. 결과로 나온 `<slug>.intake.md` 파일을 이 블로그 레포로 가져온다.
4. 블로그 레포에서: **"이 md 정리해서 글 올려줘"** + 파일 경로.

이 프롬프트는 블로그 레포의 파일을 읽을 수 없는 환경을 전제로 하므로,
필요한 규격이 전부 안에 들어 있다. 그대로 복사하면 된다.

---

--- 복사 시작 ---

너는 지금 내 개인 개발 블로그(https://dev-denver.github.io)에 올릴 글의 **재료**를 정리한다.
최종 글을 쓰는 게 아니다. 블로그 레포에서 이 재료를 받아 다듬을 것이므로,
너의 임무는 **지금 이 레포에만 있는 정보를 빠짐없이 담아내는 것**이다.

## 블로그 성격

- 학습 기록(TIL) 블로그다. 성과 발표나 포트폴리오가 아니다.
- 완성된 결론보다 **배우는 과정**이 핵심이다. 삽질하다 실패한 시도도 그대로 남긴다.
- 독자는 같은 주제를 검색해서 들어온 다른 개발자다.
- 한국어로 쓴다.

## 반드시 지킬 규칙

1. **추측 금지.** 이 레포에서 실제로 확인한 것만 쓴다. 불확실하면 지어내지 말고
   `> [확인필요] ...` 로 표시해서 남긴다.
2. **코드와 에러 로그는 원문 그대로.** 요약하거나 예쁘게 고치지 말 것. 언어를 지정한
   fenced code block을 쓴다.
3. **파일 경로를 남긴다.** 이 레포 기준 상대경로 + 줄번호
   (예: `src/main/java/com/example/auth/TokenService.java:42`). 나중에 블로그 쪽에서는
   이 레포를 볼 수 없으므로, 여기 안 적힌 건 영영 복구 못 한다.
4. **비밀정보 제거.** API 키·토큰·비밀번호·사내 URL·사내 도메인·실명·사내 레포명은
   삭제하거나 placeholder(`<API_KEY>`, `example.com`, `내부 서비스 A`)로 치환한다.
   회사 코드라면 도메인 로직이 드러나는 변수/클래스명도 일반화한다.
5. **압축하지 말 것.** 이건 초안이 아니라 재료다. 길이를 줄이려고 단계를 건너뛰거나
   시도 과정을 생략하지 않는다. 다듬는 건 블로그 쪽에서 한다.
6. 태그는 **소문자 ASCII 기술명**만 (`spring`, `jpa`, `postgresql`, `astro`).
   한글 태그는 URL 슬러그가 깨지므로 금지. 2~4개.
7. 스크린샷·다이어그램 이미지가 있으면 md에 넣지 말고, 자리에
   `<!-- IMAGE: 무엇을 보여주는 이미지인지 | 파일 원본 경로 -->` 주석만 남긴다.

## 출력

파일 하나를 만든다. 파일명은 `<slug>.intake.md`
(slug은 소문자 ASCII kebab-case, 예: `jwt-refresh-token-race.intake.md`).

형식은 정확히 아래와 같다.

```markdown
---
kind: concept | problem | retro # 아래 셋 중 하나
title_suggestion: "글 제목 제안"
category_suggestion: "언어/CS 기초 | 프론트엔드 | 백엔드/인프라 | 회고/TIL" # 넷 중 하나만
tag_suggestions: ["spring", "jpa"]
source_repo: "레포 이름 (사내 레포면 일반화)"
date_studied: 2026-08-25
---

## 배경

왜 이걸 보게 됐는지. 어떤 작업을 하던 중이었는지.

## 본문

kind별 뼈대를 따른다 (아래 참고).

## 코드 / 로그

원문 그대로. 각 블록 위에 어느 파일인지 적는다.

## 배운 점 / 남은 의문

- 배운 것: ...
- 아직 모르는 것: ...

## 참고 자료

- 공식 문서 URL
- 커밋 해시 / 이슈 링크
```

## kind별 본문 뼈대

**`concept` — 개념 정리** (뭔가를 새로 공부했을 때)

1. 핵심 개념이 무엇인가
2. 어떻게 동작하는가 — 근거(문서, 실제 코드, 실험 결과)와 함께
3. 예제 코드
4. 헷갈렸던 지점 / 처음에 잘못 이해했던 것

**`problem` — 문제 해결** (막혔다가 뚫었을 때)

1. 환경 (언어·프레임워크·버전)
2. 증상 — 에러 메시지 **원문 전체**
3. 시도한 것과 그게 왜 안 됐는지 (실패한 시도가 이 항목의 핵심이다)
4. 실제 원인
5. 해결 코드 (before / after)
6. 왜 이게 되는가
7. 재발 방지 — 다음에 같은 증상을 보면 어디부터 볼 것인가

**`retro` — 프로젝트 회고 / TIL** (뭔가를 만들었을 때)

1. 무엇을 만들었나
2. 어떤 방식을 골랐고 왜 골랐나 (검토했다가 버린 대안 포함)
3. 막혔던 지점
4. 결과
5. 다음엔 다르게 할 것
